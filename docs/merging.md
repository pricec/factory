# Merging: the normative merge-job procedure

This document is **normative** for merge jobs (spec §6.11). The factory's
merge queue dispatches one merge job at a time, pinned to the integration
foreman (`foreman:server`). The job's task text is generated by code
(`jobs.MergeTask`). It names the request and points here. A merge job
executes **this procedure exactly, every time**: every step, in order,
nothing added, nothing skipped. When a step says **STOP**, go straight to
[Reporting](#reporting) with status `failed`. The request then goes
`needs_attention`, and the factory routes it (see
[Who requests merges, and what happens when one fails](#who-requests-merges-and-what-happens-when-one-fails)).
Never improvise around a STOP.

Hard rules (they hold in every step):

- **Never touch the operator checkout `/home/price/temp/factory`.** It holds
  the operator's uncommitted work. Do not `cd` into it, and never run
  `checkout`, `switch`, `reset`, `stash`, `commit`, `clean`, `rebase` or
  `merge` there. The only allowed use is the read-only fetch in step 3, which
  reads it as a remote and writes nothing to it.
- **Never push to the default branch (`master`) directly, and never force-push anything**
  (`--force`, `--force-with-lease`, `+refspec`). Master changes only through
  `gh pr merge --merge`.
- **Work is never left unpushed.** If the requested commit exists only
  locally, push it to its branch before anything else (step 3).
- **Do not guess.** If the branch head does not match the request, STOP.
- **Act as an account that can push to `$REPO`, through `$GHAS` only.**
  The host's `gh` may be logged in to several GitHub accounts, and the
  active one need not be a collaborator on `$REPO` (`gh pr create` then
  fails with `must be a collaborator`). Every `gh` command and every `git`
  command that talks to `origin` runs as `$GHAS <command>` (step 1), which
  hands the chosen account's token to that one command via `GH_TOKEN`.
  Never run `gh auth switch` or `gh auth login`: other jobs share the
  host's gh config.

## 0. Inputs

The job payload carries the request. Set these shell variables from it.
Every command below uses them.

```sh
MR=<merge_request_id>      # e.g. mr_01J...
REPO=<repo>                # gh OWNER/REPO, e.g. pricec/factory
BRANCH=<branch>
HEAD_SHA=<head>            # 7-40 hex chars, as requested
NOTE=<note>                # PR title; may be empty
WORK=/tmp/factory-merge/$MR
EV=/var/lib/factory-foreman/evidence/merge-$MR
export PATH=/usr/local/go/bin:$HOME/go/bin:$PATH
mkdir -p "$EV"
```

## 1. Preflight

```sh
gh auth status && go version
[ "$REPO" != pricec/factory ] || sudo -n true     # only the factory deploy needs sudo
# Build the merge tools from factory master (public repo: any account can read it).
# $WORK is a clone of $REPO, which is usually NOT the factory repo, so the
# tools are built here once and run as binaries; never run `go` in $WORK.
rm -rf "$EV/factory-src" && git clone -q --depth 1 https://github.com/pricec/factory "$EV/factory-src" &&
  (cd "$EV/factory-src" && go build -o "$EV/ghas" ./cmd/ghas && go build -o "$EV/cigate" ./cmd/cigate) &&
  rm -rf "$EV/factory-src"
GHAS="$EV/ghas -repo $REPO"
$GHAS -login | tee "$EV/gh-account"     # the account every later step acts as
```

`cigate` is built the same way and takes the repo from `-repo`, so it gates
`$REPO`'s own CI runs, whatever their names.

`ghas` (`cmd/ghas`, `internal/ghaccount`) acts as the `pricec` gh account
and no other (`-account` / `FACTORY_GH_ACCOUNT` override it; the host's
other account, `chris-qunify`, is a separate identity and is never used or
even queried). It requires that account's token to have push (or maintain/
admin) permission on `$REPO`. It runs the given command with `GH_TOKEN` set
to that token; git over https picks it up through gh's credential helper.
If `pricec` is not logged in or cannot push it exits 3 and says why; there is no fallback to another account.

Any failure: **STOP** (`preflight: <what failed>`), quoting `ghas`'s
message when account selection failed.

## 2. Dedicated clean clone

```sh
rm -rf "$WORK" && mkdir -p "$(dirname "$WORK")"
$GHAS gh repo clone "$REPO" "$WORK" && cd "$WORK"
$GHAS git fetch origin --prune
```

Every later command runs inside `$WORK`.

`$BASE` is the repo's default branch, read once and used everywhere below
instead of a hardcoded name (for `pricec/factory` it is `master`):

```sh
BASE=$($GHAS gh repo view "$REPO" --json defaultBranchRef -q .defaultBranchRef.name)
test -n "$BASE"
```

If `$BASE` is empty: **STOP** (`preflight: no default branch for $REPO`).

## 3. Verify the head; push the branch first if needed

```sh
REMOTE=$($GHAS git ls-remote origin "refs/heads/$BRANCH" | cut -f1)
# The requested commit, if it exists only locally: read-only fetch of the
# branch from the operator repository's object store (writes only to $WORK).
# Only for pricec/factory: the operator checkout is that repo, and a same-named
# branch of it is not a commit of any other repo.
[ "$REPO" != pricec/factory ] ||
  git fetch /home/price/temp/factory "refs/heads/$BRANCH:refs/local/$BRANCH" 2>/dev/null || true
LOCAL=$(git rev-parse -q --verify "refs/local/$BRANCH^{commit}" || true)
```

Decide, in this order:

1. `REMOTE` starts with `HEAD_SHA`. The branch is on origin at the requested
   head. Set `FULL=$REMOTE`.
2. `REMOTE` is empty, and `LOCAL` starts with `HEAD_SHA`. The branch is not
   on origin. **Push it first:** `$GHAS git push origin "$LOCAL:refs/heads/$BRANCH"`.
   Set `FULL=$LOCAL`.
3. `REMOTE` is non-empty, `LOCAL` starts with `HEAD_SHA`, and
   `git merge-base --is-ancestor "$REMOTE" "$LOCAL"` succeeds. Origin is
   behind the requested head. Fast-forward it:
   `$GHAS git push origin "$LOCAL:refs/heads/$BRANCH"` (never forced). Set
   `FULL=$LOCAL`.
4. Anything else is **head drift**: **STOP**
   (`head drift: requested $HEAD_SHA, origin/$BRANCH is ${REMOTE:-absent}, local is ${LOCAL:-absent}`).

Then confirm:

```sh
$GHAS git fetch origin && test "$(git rev-parse "origin/$BRANCH")" = "$FULL"
```

If that fails: **STOP** (head drift).

## 4. Open (or reuse) the pull request

```sh
TITLE=${NOTE:-$BRANCH}
{ echo "Merge request $MR (factory merge queue, docs/merging.md)."; echo
  echo "Commits:"; git log --oneline --no-merges "origin/$BASE..$FULL"; } > "$EV/pr-body.md"
PR=$($GHAS gh pr list -R "$REPO" --head "$BRANCH" --state open --json number -q '.[0].number')
[ -n "$PR" ] || PR=$($GHAS gh pr create -R "$REPO" --base "$BASE" --head "$BRANCH" \
    --title "$TITLE" --body-file "$EV/pr-body.md" | grep -o '[0-9]*$')
test "$($GHAS gh pr view "$PR" -R "$REPO" --json headRefOid -q .headRefOid)" = "$FULL"
```

If the PR's head is not `$FULL`, **STOP** (head drift).

If `git log origin/$BASE..$FULL` is empty, the branch is already merged.
**STOP** (`nothing to merge`).

## 5. Wait for green checks

Never trust an existing red verdict, and never declare the merge dead on
the first red. A red check on the head may be a one-off flake, and a
request re-queued at the same head would otherwise just re-read the
previous request's failed run. The deterministic gate (`internal/cigate`)
waits for the head's runs, and if any is red it re-runs the failed jobs
once (`gh run rerun <id> --failed`), waits for the fresh attempt, and only
then decides:

```sh
$GHAS "$EV/cigate" -repo "$REPO" -branch "$BRANCH" -sha "$FULL" | tee "$EV/cigate.json"   # exit 0 green, 1 red/no checks/timeout
$GHAS gh pr view "$PR" -R "$REPO" --json mergeable,mergeStateStatus
```

Green means: `cigate` exits 0 (every run passed, at least one ran, possibly
after the one rerun) and `mergeable` is `MERGEABLE`. A rerun that turned
the head green is a **flake**: carry on, but report it (see Reporting).
Run `cigate` again only after pushing a new head (it reruns at most once
per call and never loops).

If `cigate` reports `red` (red in the rerun too), or the PR conflicts:

- **Small and clearly in scope.** The failure or conflict is in files the
  branch already changes, and the fix is a few lines with no contract or
  behavior change. Fix it in `$WORK` on the branch. Bring the base branch in with
  `git merge origin/$BASE`, never a rebase. Run the repo's own checks (`make ci` if it has a Makefile ci target, else its documented test command), then push the
  branch normally (`$GHAS git push`, no force). Go back to the start of step 5. Each extra
  commit goes in the report.
- **Anything else: STOP** (`checks red after rerun: <tests that failed both
  times>` or `conflict: <files>`). Never force-push. Never push to master.

## 6. Merge

```sh
$GHAS gh pr merge "$PR" -R "$REPO" --merge --delete-branch=false
MERGED=$($GHAS gh pr view "$PR" -R "$REPO" --json mergeCommit -q .mergeCommit.oid)
$GHAS git fetch origin && git merge-base --is-ancestor "$MERGED" "origin/$BASE"
```

If `gh pr merge` refuses (branch protection, the branch moved), **STOP**.
Never retry with admin flags.

Only `pricec/factory` and the repos in the **deploy hooks** table below have a
deploy procedure. For any other repo there is nothing to run, and that is
**not** a clean landing: the PR is merged but the change is not running.
Skip step 7, go to step 8 and report it as **`landed, NOT deployed`**
(`deployed: false`); the factory then raises an operator alert. Never report
a quiet "no deploy". Code jobs prevent this: a job that changes a deployable
service must add or keep `scripts/deploy.sh` (rollback, deploy, smoke check,
last line `DEPLOYED sha=...`) and get the repo listed in the table below.

### Deploy hooks (non-factory repos)

| Repo | Foreman | Hook (run at `$MERGED`) |
|---|---|---|
| `pricec/video-chat` | integration (default) | `scripts/deploy.sh` |
| `pricec/movies-chat` | integration (default) | `scripts/deploy.sh` (builds the Go binary, restarts `movies-chat.service`, checks `/healthz`) |
| `pricec/media-curator` | `foreman:megatron` | `scripts/deploy.sh` (runs pytest, fast-forwards the live checkout, restarts the worker gracefully, health-checks, rolls back itself) |

The table lives in this reviewed document on purpose: a repo gets host-level
deploy only when listed here, never because a merged PR added a script. A hook
runs from a clean checkout of the merged commit, on the integration foreman
(this host) unless the Foreman column names another one (see
[Remote hooks](#remote-hooks)), and must itself keep a rollback (image tag or binary copy), verify health, and restore the
previous version on failure (`scripts/deploy.sh` does all three and exits
non-zero on failure):

```sh
git checkout -q --detach "$MERGED" && git rev-parse HEAD   # == $MERGED
ROLLBACK_TAG="pre-${MERGED:0:7}" ./scripts/deploy.sh 2>&1 | tee "$EV/deploy.log"
```

Exit 0 means deployed and verified (the last log line is `DEPLOYED sha=...`);
record the sha and rollback tag. A non-zero exit means **STOP**
(`deploy: <last failing line>; rolled back: yes|no`). Never touch other
containers (workers, backfill jobs) from a hook.

#### Remote hooks

A row whose Foreman is not the integration foreman is a **remote hook**, and
the merge job does **not** run it (it would deploy on the wrong host). For
such a repo the merge job does steps 1 to 6, skips step 7, and reports
`done` with `result.merged: true`, `merge_commit` (the full 40-char sha) and
no `deployed`; summary `merged <MERGED:12>; deploy dispatched to <foreman>`.
The merge queue then (code: `factoryapp.dispatchRemoteDeploy`, hook list
`jobs.DeployHooks`, kept equal to this table by a test) re-points the request
at a **deploy job** pinned to that foreman, granted the `github-pat` secret.
The request stays `merging` and the queue stays held. The deploy job fetches
`$MERGED` one-shot (the secret inline in a single `x-access-token` fetch URL;
never written to config, remotes, files or logs), checks it out detached
in a fresh directory, and runs the hook. Verdict from exit code and last line:

| exit | last line | meaning |
|---|---|---|
| 0 | `DEPLOYED sha=<sha>` or `DEPLOYED <sha7> prev=<sha7>` | deployed |
| 3 | same | code deployed, service restart deferred (e.g. a conversion in flight): still deployed, `result.restart_deferred: true` |
| other | any | failed (the script rolls itself back) |

The sha must be a prefix of `$MERGED`. The request lands as deployed only on
the deploy job's `deployed: true`; a failure reports `stage: deploy`, the same
escalation as an in-host deploy failure (P1 alert, no auto-fix, no retry).

## 7. Deploy master

Run [docs/operator-runbook.md § Deploying master](operator-runbook.md#deploying-master)
exactly, with `REF=origin/master`. Its result must contain `$MERGED`
(check with `git merge-base --is-ancestor "$MERGED" "$DEPLOYED"`).
`$EV` is its evidence directory. The runbook's own failure steps (rollback
before the manifest) are part of this step. A deploy failure means
**STOP** (`deploy: <check that failed>; rolled back: yes|no`).

## 8. Verify and report

For a repo with a deploy hook, the hook's own verification (step 7; for a remote hook, the deploy job the queue dispatches) is the
check; it must include a smoke check of the running service. For any other
repo there is nothing to deploy: report `landed, NOT deployed`. For `pricec/factory`, re-check right before reporting:

```sh
systemctl is-active factory
curl -fsS -o /dev/null -w '%{http_code}\n' http://127.0.0.1:8090/        # 200
go version -m /usr/local/bin/factory | grep -o 'buildinfo.ID=[^"]*'      # == build in dist/manifest.json
```

On success, `rm -rf "$WORK"`. On failure, leave it for the operator. Then
report.

## Reporting

Call `report_result` once, at the end:

- **done**: only when the PR is merged and, for `pricec/factory`, the deploy
  is verified healthy (and for a deploy-hook repo, the hook succeeded). For any other repo, `done` means merged and **not deployed** (see below). `result.merged` must be `true`; the queue lands the
  request only then (a `done` without `merged:true` is `needs_attention`). Summary (240 chars max):
  `landed $MR: PR #<n> merged <MERGED:12>; deployed <build id>; exe sha ok, UI 200, journal clean`.
  `result`: `{merged: true, pr, merge_commit, deployed_commit, build_id, factory_exe_sha256, evidence_dir}`.
  For a non-factory repo the summary is `landed, NOT deployed $MR: PR #<n> merged <MERGED:12>; no deploy step for <repo>`
  and `result` is `{merged: true, pr, merge_commit, deployed: false, evidence_dir}`.
  The factory marks the request `landed, NOT deployed`, raises a P1 operator
  alert and tells the owning task it is not done. `deployed:true` (or a
  non-empty `deployed_commit`) is required for a clean landing.
  For a hook repo (table above) the summary is `landed $MR: PR #<n> merged <MERGED:12>; deployed <MERGED:7> (rollback <tag>)`
  and `result` is `{merged: true, pr, merge_commit, deployed: true, deployed_commit, smoke, rollback_tag, evidence_dir}`; `smoke` names the check that passed (e.g. `/healthz 200`).
  If `cigate` reran and went green, add `ci_rerun: true` and `ci_flaked: [tests]`
  to `result` and append `; CI flake rerun: <tests>` to the summary, so flakes stay visible.
- **failed**: anything that stopped. The summary starts with the stage, for
  example `head drift: …`, `checks red after rerun: <tests failed both
  times>`, `conflict: …`, `deploy: …`. Also set **`result.stage`** to the
  stage that stopped, exactly one of `preflight`, `head_drift`,
  `nothing_to_merge`, `ci`, `conflict`, `merge`, `deploy`: the factory
  routes the failure on it (the summary prefix is only the fallback). For
  red checks, put the `cigate`
  output (`rerun`, `first_failed`, `second_failed`, `failed_both`) in
  `result` so the alert shows that a rerun happened and what failed.
  Always set `result.merged: false` and `result.reason` (e.g. `conflict`)
  when nothing was merged, and report `failed`, never `done`.
  `error`: `{"kind": "other", "message": "<stage>: <detail>"}`. Include
  `pr` / `merge_commit` in `result` when they exist, because a failure after
  the merge (in deploy) means master moved.

The merge request closes from this job's terminal state. Merge jobs start on the default tier; a `ci` or `conflict` failure is
re-run once on the hardest tier by the factory (spec §6.11). Merge jobs never
otherwise retry, and a merge job never fixes more than step 5 allows.

## Who requests merges, and what happens when one fails

This section is for everyone except the merge job (spec §6.11, "Job-owned
merges").

**The job that wrote the branch requests its merge.** A code-change job
works on a branch, merges `origin/master` into it (merge, never rebase;
resolve conflicts), gets CI green on that merge result, pushes, and then
calls the worker tool `request_merge(branch, head, note?, after?)` itself, before it reports
done. The planner does not queue routine merges and does not have to
remember a follow-up. The operator can still queue a merge by hand (UI,
`POST /v1/merge-requests`), and the planner has `request_merge` for a
branch no job queued.

- `head` pins the commit: the merge job stops with head drift if the
  branch is anywhere else. A job that pushes one more commit calls
  `request_merge` again with the new head; its still-queued request is
  replaced. A request that is already merging is never replaced.
- `after` is the dependency gate: "queue this after branch X merges". The
  request stays queued, without blocking the queue, until a merge request
  for every named branch (same repo) has landed. Use it when the branch
  needs another job's branch on master first. If the dependency's merge
  fails for good or is cancelled, or nobody queues it within an hour, the
  planner is told: sequencing the work of different jobs is its
  coordination job.

**The factory tracks the outcome against the requesting job's task.**

| outcome | what the factory does |
|---|---|
| landed | Notes it on the task and wakes the planner once, to tell the operator. |
| failed, fixable by the branch's author: `ci`, `conflict`, `head_drift` | Dispatches a **merge-fix job** on the same branch, on the foreman that ran the requesting job, linked to the same task. It fixes, runs CI, pushes and calls `request_merge` again. No alert, no planner session. |
| failed, anything else: `deploy`, `preflight`, `merge`, `nothing_to_merge`, no report | P1 alert for the operator, linked to the task, and the planner is woken to coordinate. |
| failed after 2 merge-fix jobs | The same escalation. The loop is bounded: there is never a third fix job for one chain of requests. |

**Merge events never create tasks.** A failure, conflict or stalled
dependency is posted on the owning task's thread as an internal
`notify.merge`; the planner there files a fix or rebase job. The same
event twice posts nothing (no repeated wake), and events for a request
already landed or cancelled are ignored. If the owning task is closed it
is **reopened** with a note when the event needs the planner (landed and
cancelled stay recorded only). If no task owns the job, the note goes to
the standing Planner chat when it exists, else a P1 alert is raised;
still no task is created. Spec §6.11.

A job's declared `touches` (spec §6.14) keep conflicting jobs apart: a job
whose `touches` overlap an active job's is held until that job's merge
request lands (or is cancelled or needs attention), so merge conflicts
between concurrent jobs are rare. The merge job itself and merge-fix jobs
are never held by it.

A request with no requesting job (operator, planner) fails as before: P1
alert, and re-requesting is the operator's call. Auditor auto-fixes keep
their own path (spec §6.12).

Nothing here changes the procedure above: every merge, whoever requested
it, is one merge job running steps 0 to 8, with the pinned head, the one
CI rerun and the deploy health check.
